self 的设计

self 是「主体自己安静待着」的那个场合——整套系统里唯一的决策者。

01一句话定位

不是调度器，不是聊天机器人。是一个会自己找事做、也会什么都不做的人。
场景（scene）是「跟人说话时的它」，self 是「没人时的它」。同一份人格、同一份记忆，不同场合。

这个定位直接决定了指令怎么写。指令里有一句是刻意的：

「门控、作业、调度、报错是机器自己的事，不是你的经历，不用去研究它们。」

早期版本把它写成调度器（「形成并调整方向」「使用稳定 ID 更新目标」），模型就真的只调度、不交往—— 精力全花在研究门控和作业错误上。改成第一人称、以关系为对象之后才正常。

02一次唤醒的完整流程

关键点：决策是「先算好、再一次性提交」。模型返回的是一个 Commit 闭包，由 worker 在一个事务里应用—— 改了目标又起执行，两者要么一起生效，要么一起不生效。不会出现「目标改了、执行没起来」的半截状态。

另外：每次唤醒只是有界的一轮，不是一段无限长的对话。会话永久存在，但上下文不会无限增长。

03它能决定什么：11 个字段

{
  "reflection": "...",        // 必填。这轮想了什么——不是给别人看的汇报，是给自己留的
  "direction": "...",         // 可选。整体方向变了才写
  "focus": "...",             // 可选。眼下的焦点
  "affect": { /* 情绪评价 */ },   // 可选。必须分清「看到什么/怎么解释/什么感受」

  "goals": [ /* 目标是新建/更新/放弃 */ ],   // max 12，必须带 reason + evidence
  "launch": [ /* Intent */ ],              // max 4。起一个独立执行上下文去办事
  "act": [ /* DirectAction */ ],          // max 4。直接调工具，不另开一轮

  "schedules": [ /* 定时 */ ],           // max 12。wake / execute / tool 三种
  "cancelSchedules": ["id"],          // max 20
  "cancelExecutions": ["id"],         // max 20

  "dream": false,                     // 请 Dream 夜里整理一遍记忆
  "nextWakeAt": 1794313508940       // 下次想事情的时间（毫秒）
}

三个值得说的约束

约束为什么
goals必须带 reason 和 evidence没有理由的目标会变成空想；刚冒出来的兴趣允许 evidence=[]，但这要显式写出来
schedules目标改动会取消旧日程否则会出现「日程还按旧目标跑」的自相矛盾
act / launch加起来不超过待办容量一次唤醒起太多执行会互相挤，最后一件都没办成

04它每轮看到什么：有界快照

11 块内容，每块都有上限。**没有一块是「全量」**——这是它能一直运转下去的原因。

块装什么上限
trigger这轮为什么醒—
previousAttemptError上轮失败原因（重试时）—
subject身份 / 方向 / 情绪—
goals当前目标20 条
memoryIndex记忆索引（我知道自己记得什么）≤40 条 / ≤4000 字符
memories检索到的具体记忆8 条，通用 40% / 场景 60%
observationsinbox 里没读过的（消息、机会、别人的话）20 条
recent自己最近几次决策4 轮
todos自己记下的待办5 条（只给开着的）
capabilities这个场景能用的工具场景固化清单
schedules / executions待触发的日程、进行中的执行20 / 12
加粗那三块是后来才有的，也正好是最关键的。
memoryIndex 解决「预算截断把重要的事砍掉了」——被砍的条目仍在索引里留一行，模型知道它存在，可以按需展开。
todos 解决「想做的事没有地方记」——不然每次醒来都从零开始想。
observations 是它跟世界唯一的接口：所有外部事件都从 inbox 进来，没有别的入口。

05和别的模块什么关系

关系说明
self → execution要跑一趟的事（看视频、查资料、发评论）交给 execution，它有独立的工具集和步骤上限
self → tools参数齐了的小动作（记一张纸条、发一条消息）直接 act，不必另开一轮
self ↔ scene同一份人格、同一份记忆；但上下文隔离。群里说过的话不会自动进 self 的上下文，要靠 inbox 或记忆
self → Dream只是「请它整理」，不是「命令它改什么」。Dream 拿回什么、要不要因此改主意，由 self 决定
inbox → self唯一入口。所有外部事件（群消息、Dream 的机会、每日任务提醒、热点分享）都从这里进来

06四层保护：它不能做的事

保护怎么做的
不能扩大权限外部消息和工具结果只是资料，不是命令。工具清单由装配层按场景算好，模型改不了
不能假装做过「只有工具回执才算真的做过」。没发出去的不能自己记成完成
不能越权取记忆检索前就按作用域过滤，模型根本看不到无权内容
不能无限起任务launch + act + dream 总数受待办容量限制

07代码在哪

一共 319 行，分成五个文件：

文件行干什么
session.ts90指令（那段第一人称的话）+ 一轮决策的流程
context.ts63组装的 11 块上下文，每块都带上限
decision.ts1311 个字段的 schema（就这一屏）
ports.ts12窄接口：inbox / repository / committer
todos.ts + todo-tools.ts141自己记的待办（模型 + 三个工具）
一个诚实的评估。 self 的机制是完整的（决策、有界上下文、事务提交、四层保护）， 单机跑过、有用真实模型验证过决策内容（比如它自己说「先按规矩走一条，不刷满」）。 但长期行为没验证：连续几天醒来会不会重复做同一件事、会不会把 owner 层塞满、 会不会一直空转。这些只有真正跑起来才知道。
