记忆存储实录

下面每一段都是从一个真实生成的 agent.sqlite 里 sqlite3 dump 出来的，不是设计描述。

01一个库文件的全部内容

整个 agent 就一个 SQLite 文件。里面 8 张表 + 9 个索引：

table | documents      ← 小集合用文档存（人物、索引、goals、meta…）
table | memories       ← 记忆主体，关系表
table | memory_evidence ← 证据指针，可反查
table | experience     ← 经验流水（append-only）
table | turns          ← 会话决策记录
table | jobs           ← 任务队列
table | seen_events    ← 去重
table | model_calls    ← 模型调用计数（限流）

index | memories_scope   (scope, status, updated_at DESC)
index | memories_subject (subject_user_id, status)
index | memories_stale   (status, last_accessed_at)
index | memories_updated (updated_at DESC)
index | memory_evidence_seq (seq)
index | experience_source, jobs_active, jobs_due, turns_session

02记忆本体：memories 表关系表

CREATE TABLE memories (
  id              TEXT PRIMARY KEY,
  content         TEXT NOT NULL,              -- 只有这一句会进上下文
  scope           TEXT NOT NULL DEFAULT 'owner',
  subject_user_id TEXT,                       -- 这条事实关于谁
  visibility      TEXT NOT NULL DEFAULT 'group',
  origin_user_id  TEXT,                       -- 谁说的（群内可见的个人事实需要它）
  kind            TEXT NOT NULL DEFAULT 'observation',
  fact_type       TEXT,                       -- preference/fact/boundary/event/open_loop
  mention_policy  TEXT,                       -- 能不能主动提
  persona_summary TEXT,
  status          TEXT NOT NULL DEFAULT 'active',
  importance      INTEGER NOT NULL DEFAULT 1,
  confidence      REAL NOT NULL DEFAULT 1,
  revision        INTEGER NOT NULL DEFAULT 1,
  merged_into     TEXT,                       -- 被压缩进哪一条
  source_event_id TEXT,
  expires_at      INTEGER,
  last_accessed_at INTEGER,                   -- 上次被想起来（归档判断用）
  access_count    INTEGER NOT NULL DEFAULT 0,
  created_at      INTEGER NOT NULL,
  updated_at      INTEGER NOT NULL,
  evidence        TEXT NOT NULL DEFAULT '[]'  -- 指向经验流水的 seq 列表
);

candidate还没确认默认不会

为什么不用 JSON 数组就完了

因为要能反问：哪些记忆引用了第 100 条原话？

SELECT memory_id FROM memory_evidence
WHERE seq=100;
→ mem-a1

撤回一条原话时，就知道该连带处理哪几条记忆。

07索引真的在用（EXPLAIN QUERY PLAN）

这是 SQLite 自己的查询计划，不是我说的：

-- 候选池：按作用域取
SEARCH memories USING INDEX memories_scope (scope=? AND status=?)
USE TEMP B-TREE FOR ORDER BY      ← 这个限制见下面说明

-- 归档扫描：每天跑一次
SEARCH memories USING INDEX memories_stale (status=? AND last_accessed_at<?)

-- 按人取事实：写人物画像时用
SEARCH memories USING INDEX memories_subject (subject_user_id=? AND status=?)
一个没解决的限制。ORDER BY updated_at 仍然走临时 B 树——因为 status IN (...) 是多值， SQLite 用不上索引里后续列的排序。要消掉得拆成 UNION 或改成单值 status。 几千条的规模下不值得，所以留着并写清楚，而不是假装没有。

08一次对话是怎么落进去的

① 消息进来（不等模型，直接追加）
   INSERT INTO experience(at, source, kind, data)
   VALUES (1794313508940, 'session:group-330707267', 'message',
           '{"nickname":"牢e","text":"华师那个保研项目是校企合作"}');

② 顺手认人（代码做，不调模型）
   -- 观察到 userId + nickname → upsert 到 documents 的 people 集合

③ 夜里 Dream 提炼（这一步才调模型）
   INSERT INTO memories (...) VALUES (...);
   INSERT INTO memory_evidence(memory_id, seq) VALUES ('mem-b1', 102);
   -- 同一次里还会：升级到 owner、合并重复、重建索引、归档冷掉的、写人物画像

④ 下次醒来读
   SELECT * FROM memories
   WHERE status IN ('active','candidate') AND scope IN ('owner', 'group:330707267')
   ORDER BY updated_at DESC LIMIT 160;        -- 走 memories_scope
   -- 再在内存里按 access.ts 验权、分池、IDF 排序、预算渲染

09一句话总结

东西存在哪怎么取
记忆memories 表（关系表）按 scope/status 走索引取候选池，再内存里排序渲染
证据memory_evidence 表按 seq 反查，或按 memory_id 取全部
经验流水experience 表按 seq 游标增量读
人物documents / collection=people按 userId 取整条 JSON
索引documents / collection=memory.index按 scope 取整条 JSON
目标/场景/日程/待办documents 各集合按 id 取整条 JSON
为什么不全用关系表，也不全用文档。 记忆每天 12 条、一年 4 千、过滤条件多 → 关系表值得； 人物 200 个、索引每作用域一份、目标几十个 → 永远按 id 取整条，建表只会多出一堆没人查的列。 判断依据是「这个集合将来会被按字段查吗」，不是「统不统一」。
