记忆机制：设计与产物

不讲流程，先讲清楚每层沉淀下来的东西到底是什么样，再讲它们怎么产生、怎么用。

00总体设计

要解决的问题只有一句

下次醒来，怎么在有限的上下文里，用一个不像失忆的人的方式，接上上次的事。

「有限上下文」是硬约束——不可能把所有历史都塞进去。「接上」是目标——不是查询，是能自然地接着说话、接着做事。 两者冲突，就产生了分层：越靠上层越精简、越常驻；越靠下层越具体、越按需。

五层产物，粒度递减、数量递减

为什么是四层而不是一层。一层的话只能二选一：要么全量塞进去（上下文爆），要么只留摘要（细节没了）。 四层的做法是——摘要常驻，细节留档：索引告诉你「有这件事」，一条代码指向具体记忆；真要用时再展开。 这正是 Claude 的 MEMORY.md 干的事，只是这里按作用域分成了多份。

01产物一：经验流水append-only

原材料。发生什么就照抄什么，不做任何判断——判断留到提炼阶段，这样写路径不会被模型耗时卡住。

{
  "seq": 4821,                       // 单调递增，游标靠它推进
  "source": "session:group-330707267",  // 来自哪个场景
  "kind": "message",              // message / tool_result / note / dream …
  "data": {
    "nickname": "某群友",
    "text": "华师那个保研项目是校企合作，成果要挂企业名",
    "userId": "1602…"
  },
  "at": 1790339103000
}
按 seq 读
每个消费者（self / scene / dream）记自己的游标，从上次的位置继续
只追加
不改不删。所以「我当时原话是什么」永远查得到，是后面所有证据链的根
没有重要性
这里不判断值不值得记。判断在下一层，可以有模型参与——写路径不能等模型

02产物二：记忆提炼后的判断

这是核心产物。一条记忆 = 一件被确认的事实 + 它凭什么成立 + 它属于哪个场合。

{
  "id": "mem-7f3a",
  "content": "他最终选了华师保研，但担心校企合作项目的就业风险",   // ← 只有这一句会进上下文

  "scope": "group:330707267",     // 只在这个群成立
  "subjectUserId": "1602…",      // 这条事实关于谁
  "visibility": "personal",      // 谁能看：personal 只给本人相关场景

  "evidence": [4817, 4821],          // 指向经验流水的 seq —— 凭这两句原话
  "kind": "observation",           // observation 看到 / inference 推断 / strategy 策略
  "factType": "fact",              // fact / preference / boundary / event / open_loop …
  "confidence": 0.82,              // 有多确定
  "importance": 4,                 // 对理解这个人有多关键（0-5）

  "status": "active",             // active / candidate / archived / superseded
  "revision": 3,                    // 改过几版；旧版单独留档
  "mergedInto": null,                // 被压缩进哪一条

  "createdAt": 1790339103000,
  "lastAccessedAt": 1791465183000, // 上次被想起来 —— 归档靠它判断冷没冷
  "accessCount": 3,                 // 常用说明还有用，不归档
  "expiresAt": null,                 // 有时间性的事实才填
  "mentionPolicy": "soft_echo"      // 能不能主动提：direct / soft_echo / tone_only / avoid
}

这些字段不是随便加的，每个都在挡一种具体的错误

字段挡住的错误
evidence模型编造一件事。每条都必须能指回原话，否则 Dream 回放时无法核对
scope在 A 群听到的事跑到 B 群说漏。过滤在检索前，模型根本看不到无权内容
visibility + subjectUserId把别人的私事带进不属于它的会话。「事实关于谁」和「谁能看」是两件事，不能混用
confidence把「他可能喜欢」当成「他喜欢」。低置信度的需要更多证据
status已撤回的事还挂在上下文里。candidate 是还没确认的，不默认注入
revision + mergedInto改过之后丢了原版。旧版单独留档，能追「当时是怎么说的」
lastAccessedAt + accessCount记忆只增不减。这两个是归档的唯一依据，让遗忘有据可依
mentionPolicy该记但绝不能主动提的事（别人的隐私）。记着，但只用作背景判断

03产物三：索引目录，常驻

记忆是「存着什么」，索引是「知道自己存着什么」。每次注入都带上它，细节靠 memory.expand 按需取。

{
  "scope": "group:330707267",   // 每个作用域一份，owner / group:xxx / feature:xxx
  "version": 12,                   // 每次重建 +1
  "updatedAt": 1794288000000,
  "entries": [
    {
      "topic": "择校与保研",
      "summary": "纠结华师/深大/杭电，最终选华师保研，担心校企合作就业风险",   // ≤60 字
      "memoryIds": ["mem-7f3a", "mem-8b21", "mem-9c04"],  // 展开时取这些
      "weight": 5                    // 超预算时先丢权重低的
    },
    {
      "topic": "408 备考",
      "summary": "目标 110-120，真题刷多遍，关注模拟卷与时间分配",
      "memoryIds": ["mem-1a2b", "mem-3c4d"],
      "weight": 4
    }
  ]
}

三条硬约束（和 Claude 对齐）

  • ≤40 条、≤4000 字符。索引是常驻的，不能变成第二份全量记忆。超了按 weight 丢行——丢的只是索引行，记忆本身还在，仍可搜索。
  • 每条必须指向真实记忆。pruneDangling 会丢掉指向空处的条目：一条指向空处的索引比没有更糟，模型会以为自己记得那件事。
  • 全量替换，不是增量。索引的价值就在于是「当前全景」；增量改几次之后会变成历史补丁的拼接，谁也不清楚里面还有效的有多少。
实测：线上 275 条真实记忆 → 20 条索引、1798 字符。主题划分和摘要都准确 （「择校与华师保研」「牢e bot 运维」「408 备考与策略」）。按场景分开后，两个群的索引完全不串。

04产物四：场景现场对话连续性

前三层管「记得什么」，这一层管「刚才聊到哪」。场景每次只读最近 20 条经验，更早的如果没有它就直接丢了。

{
  "sceneSummary": "从模拟卷质量吐槽转到「雨姐」身份确认，又跳到实习风口",

  "activeThreads": [                        // 还在继续的话题
    { "summary": "吐槽各机构模拟卷互相抄真题", "participants": ["ace", "Moretti"] }
  ],
  "openLoops": [                            // 还没接住的话 —— 这一栏最有价值
    { "summary": "「我嫌弃她有点笨」指谁没说明", "owner": "牢e" },
    { "summary": "「不是说26很简单嘛」没人接" }
  ],
  "participantStances": [                  // 谁明确表过什么态（不推测）
    { "participant": "牢e", "topic": "实习", "stance": "风口变化快，不太对劲" }
  ],
  "callbacks": [                            // 可以接回的梗，带时效
    { "summary": "雨姐=东北御姐", "ttlTurns": 15 }
  ],
  "botContinuity": {                        // 只记我真的说过的，不推测
    "recentStatements": ["名字记下了，主人这头衔谁批的呀"],
    "commitments": [],
    "stances": []
  },
  "corrections": ["他说 26 英一不难，之前记反了"]  // 纠正优先于旧说法
}

三条边界

  • 只保留影响接话的内容。人物档案、知识事实属于记忆层，不属于现场。写多了就把现场变成第二份记忆。
  • 删掉已结束的。被回答的、撤回的、被后文否定的，不再挂着。
  • 分清谁说的。botContinuity 只记原文里真的说过的——群友的提议不能变成我答应过的事。

05产物五：人物记住人

前面四层都是「按事实组织」。但人不是事实的集合，是事实的收敛。

为什么需要单独一层。真实数据里一个人有 63 条散落的事实（牢e 就是）， 但没有任何地方把它们拼成「这个人是谁」。每次注入只捞到其中几条， 于是永远拼不出一个人——bot 会记得「他选了华师保研」， 却不知道「他是群里做 408 答疑和 bot 开发的那个人」。 
{
  "userId": "3485823460",          // QQ 号唯一确定一个人，跨群是同一个人
  "names": ["ending_walker03", "牢e", "群友3460"],  // 群名片会变，名字只增不减

  "portrait": "群里的计算机考研/408 答疑与规划者，也做 QQ bot 和 LLM 工具开发",
                                    // ← 一句话画像，Dream 写，≤200 字
  "portraitEvidence": ["mem-118", "mem-166", "mem-179"],  // 凭什么这么说
  "notes": [                       // 近况：会过时，每轮被新的替掉
    "国庆期间学习欲望强，自称「读瘾犯了」",
    "正在用其他方式重做 bot；原 bot 失效，只能读群消息不能回复",
    "有代码课，每天直播讲并有录播",
    "可私聊提供 28 规划咨询和 27 真题复盘"
  ],

  "groups": ["330707267", "866795853"],  // 在哪些群见过他
  "firstSeenAt": 1790339103000,
  "lastSeenAt": 1791465183000
}

画像和事实的分工

记忆（事实）人物（画像）
粒度一条一件，可考证一句话 + 几条近况
来源逐条提炼从该人的全部事实收敛而来
谁写Dream 逐条判断Dream 看到全部事实后写
更新可改、可合并、可归档整体替换——一堆「补充说明」加起来不是画像，是又一份事实列表
注入检索命中才给最近见过的人给一小份卡片

三条约束

  • 只写有证据的判断。portraitEvidence 必须指向真实记忆；没有证据的判断不要写——画像会被当成「我一直知道的事」，写错了比空着糟糕得多。
  • 不写隐私细节。住址、联系方式这些留在记忆里（受 visibility 管），不进画像（画像会被注入到所有相关场景）。
  • 称呼用真实的，不用系统占位名。真实数据里最近见到的往往是自动生成的「群友3460」，而人实际叫「牢e」——displayName 会跳过这类占位名。
实测：用线上真实的 63 条记忆生成画像，输出是 「群里的计算机考研/408 答疑与规划者，也做 QQ bot 和 LLM 工具开发；问择校、真题复盘或 bot 实现较合适」 + 6 条近况 + 8 条证据。63 条散落事实收敛成了一句能直接用的人话。

06这些产物怎么产生

刻意分开：写路径不能等模型（会卡住对话），提炼可以慢（夜里批量做）。 这也是「经验流水」存在的理由——它是缓冲，让两件事不需要同时发生。

07这些产物怎么被使用

// 一次注入，模型实际收到的三块内容（按顺序）

① 索引（常驻，两份）
   ## 我记得的事                    ← owner 那份
   - [偏好] 他喜欢别人叫全名（展开: mem-1a2b）
   - [长期目标] 明年考 408（展开: mem-3c4d）

   ## 在这处我记得的事               ← 当前场景那份
   - [择校] 最终选华师保研，担心就业风险（展开: mem-7f3a, mem-8b21）

② 检索到的具体记忆（分池）
   general（通用层 ~40%）  2 条
   scoped（当前场景 ~60%） 3 条

③ 我认识的这些人
   ## 我认识的这些人
   - 牢e：群里的 408 答疑与规划者，也做 bot 开发
     · 正在重做 bot；原 bot 失效
     （依据: mem-118,mem-166）

④ 场景现场（只有群聊场景有）
   这段对话之前聊到（不是这一轮的原文，是背景）
   - 还没接住：「我嫌弃她有点笨」指谁没说明

// 需要细节时
memory.expand(["mem-7f3a", "mem-8b21"])  → 取全文
memory.search("华师 保研")                → 主动回想，连归档的一起翻

四次过滤，都在检索之前

过滤挡掉什么为什么必须在检索前
作用域别的场景的记忆先召回再让模型「忽略」是自欺：模型一不听话就泄露了。过滤在候选池阶段完成，模型根本看不到
状态已撤回 / 已归档 / 过期 / 候选池归档的默认不进来，但主动回想时可以（可逆）
分池一层挤掉另一层只按分数排，更「贴题」的场景记忆会把通用偏好挤光，模型就永远学不到「这个人说话喜欢怎样」
预算超长条目整条跳过，不截半句——截断的前半句最容易被当成完整事实

08Dream：重构动作

前面所有产物都可能在 Dream 这里被改写。这是整套机制唯一「重构」的地方。

09关键取舍

取舍选了为什么，代价是什么
隔离 vs 共享分层（owner 共享 / 场景隔离） 线上原版是跨群绝不可见，代价是同一个人换群就变陌生人。分层要求多维护一层「什么该放 owner」的判断
删除 vs 归档归档，可逆 删除空间省得干净，但判断错了就没救。归档要多维护一个 revive 路径
截断 vs 整条跳过整条跳过 截断能塞进更多信息，但半句话最容易被当成完整事实。代价是浪费预算
模型判断 vs 代码规则判断给模型，语义给代码 代码规则可预测但僵硬（字面相似度实测完全不管用）；模型灵活但会漂。所以把「不能错的」（证据、上限）留在代码
事实 vs 画像两者都要，单独立一层 只有事实则拼不出人（63 条散落）；只有画像则没法考证。代价是多维护一层收敛逻辑
全量 vs 增量索引全量替换 增量省 token，但几次之后索引变成补丁拼接，没人知道里面还有效的有多少。代价是每次都要看全部
这图里哪些验证过、哪些没有。
验证过（用线上真实数据：287 条记忆 + 两个真实群的 60 条对话）：分层隔离零泄漏、提升后跨群可见、压缩证据一条不丢（287→280 条，证据 287→287）、归档可逆、分场景索引分得开、IDF 改善排序、对话压缩压出可用的现场（含三个「没接住」的细节）。
没验证：长期跑下来索引会不会漂移、四项全开时一次 Dream 的 token 成本、归档会不会误伤、模型判断「该不该通用」在真实对话里准不准。这些要接真实群聊跑一段时间才知道。
